## file

Capture builds a self-contained Git repository under the artifact directory. The shared change module snapshots the target directly into that repository's object store (the author's objects are only an alternate); `pack-objects --revs --window=0` then writes exactly the objects both trees reach as one pack, reusing stored deltas without a new delta search; `checkout-index --index` materializes the head tree with raw flags. The source directory contains two synthetic commits (`base` and `review`); the manifest separately retains the original resolved endpoints. Reviewers can use ordinary Git there after the original repository disappears. This is source fidelity, not a sandbox: symlink text stays literal, and destinations outside or absent from the snapshot are explicit limitations.

Mutable capture snapshots the target again after materialization and compares commits, trees, the index tree, the stage-0 index entries (write-tree omits intent-to-add entries) and explicit intent. This detects observed concurrent changes, not an atomic filesystem snapshot. A failed capture removes only the newly created artifact. An existing destination and a destination inside the author's worktree are refused before ownership is acquired.

Git treats the empty tree as a virtual object in some commands. Store it with `mktree` so a retained root-commit capture also passes `fsck` independently.

Non-UTF8 blobs among changed paths are binary obligations: private info attributes keep Git from turning them into lossy Unicode text. Pointer detection reads only blobs under 1 KiB, using `ls-tree -l` sizes. Regions come from one `--unified=0` diff split at `diff --git` headers and zipped with `--name-status -z`, which share Git's path order; a type change (T) is written as two sections for one path. A count mismatch fails rather than misattributing a hunk. The first text region retains the file header, including modes; rename records are separate from the deterministic no-renames region inventory. Requested paths narrow coverage, not the surrounding source available to reviewers.

verifyArtifact checks the manifest, comparison and `fsck`, then hashes every materialized file and link in-process against the retained head tree, checking modes and that every parent is a real directory. It deliberately ignores the checkout's index and Git config: reviewers' ordinary Git use can set assume-unchanged or skip-worktree, restore stat data or point `core.worktree` elsewhere, and a review found each of these hid edited bytes from an index-based check. Hashing in-process with OpenSSL is faster than `git hash-object` (sha1dc) and needs no index lock. Capture itself only checks the manifest and comparison; fsck runs at full verification.

Source browsing (verifyCapturedSource) verifies the retained manifest/Git comparison and reads recorded tree objects, not the materialized files or original checkout. Full verifyArtifact still guards recovery and decisions; browsing is not that check and is not live freshness. Symlinks expose link text only; submodule and LFS pointers stay visibly separate from their referenced content.

Measured on this checkout (4,995 files): a commit capture took 22.8 s and a working-tree capture 31.8 s with per-file Node copies, per-path diffs and a full byte comparison. The Git-native capture alone takes about 2.7 s but no longer ends with full verification; compare capture plus its first full verification, which the runtime performs before reviewers start. Bulk check-in (`core.bigFileThreshold=1` on `git add`) writes new blobs into one pack: on this machine creating thousands of small files dominated (5,000 loose blobs took 3.5 s, the same blobs as one pack 0.8 s). Materializing reviewers' checkout is the remaining cost that grows with tree size (about 4.4 s for 20,000 files here). Single local observations, not a latency guarantee; see the task benchmark.
