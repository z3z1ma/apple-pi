The runtime owns this writer and its capture promises. A requesting socket closing cannot cancel an admitted operation. Enqueue commits an identity and command-result pointer before capture, but only a verified artifact enters the queue. The original command's applied receipt means target admission, not review completion.

An enqueue can bind expectedDigest from a UI preview. Compare it only after a full verified capture and before making the job queued. A mismatch remains a failed, unadmitted request with no reviewer attempt; replay preserves that original binding. Preview scratch is never adopted as runtime-owned source.

Empty in-scope changes settle as no-changes during admission, before the worker can claim them. This includes a path-filtered comparison whose surrounding source changed. Retain the artifact but create no attempts or unfinished review responsibility; cancellation and exact replay preserve the distinction from completed inspection. Runtime departure/move guards and the queue action menu share this terminal meaning.

SQLite and source acquisition have no shared transaction. After restart, an interrupted capture without a recorded artifact requires a new capture; resume never substitutes current live source. A verified artifact survives restart and must pass integrity checks again before resume. The resume update also binds the observed generation, owner and assessment revision so concurrent cancellation or reassignment cannot silently acquire an old request. Cancellation completion binds the generation it cancelled: two cancel requests can await the same cleanup independently, and a later authorized extension may queue a new generation between their completions. The old completion is then an applied no-op, not cancellation of the newly authorized work. A deterministic child-runtime test releases the two real cleanup polling timers separately to reproduce that interleaving.
Why: asynchronous cleanup lets two admitted cancellations settle on opposite sides of another authorized admission. Completion must retain its original generation authority without treating an already completed old request as authority over new work.

Organization scope follows the recorded root using the existing work-task tree semantics. Lasting people own durable reviews; temporary program peers cannot own one. Pending reviews block irreversible departure and reporting moves that would strand their owner outside the recorded organization. These checks belong with the shared runtime responsibility guards, not with each UI.

The queue claims jobs serially in priority/FIFO order and runs planning, then the focused and integration inspections concurrently (at most REVIEW_PASS_CONCURRENCY = 8, the operator's choice; an 18-pass review ran one pass at a time, about 12 minutes per pass), then validation over every report. The first failed pass aborts the rest, and all started passes settle, including reviewer cleanup, before the job fails. Inspections never read each other's reports, so their order does not matter; tests must not assume attempt creation order.

The planner names scopes by paths and chooses passes by risk; the runtime maps regions to scopes (chunkRegions) and the integration pass always receives every region, so unscoped regions are reported, not a plan failure. validatePlan checks only identities, roles and requested lenses. Plans recorded before this change name regions per chunk and remain readable.

Validation is sharded: one validator per report, in parallel under the same limit, then a duplicate-linking attempt selected as "validator". Its validate step combines the shard outputs into one FindingValidation, so readers and decisions keep a single validation; a reused merge attempt stores that combined result, which combineValidation re-checks as-is. Shards are selected as validator:<pass>. Each shard with confirmed findings mails the owner at once (key findings:<pass>), with the finding IDs resolve_finding takes; duplicates are linked only by the merge, which the stream says.

A comment is a review operation, not ordinary mail, so anyone who can read the review may add one without first being a thread member: the runtime joins the commenter (pull) and posts on review:<id>, and the owner is pushed it like any reply. A comment that arrives before any milestone first opens the thread as the harness's, with the owner on push, so later milestones can post and an owner's own first comment has an audience; a review found both failures. Unlike a milestone, a failed comment post fails the command; the result pointer is committed after the post, and restart recovery treats a stored comment message as applied even when the pointer was lost.
Every operation commits its command-result pointer (`commit(commandId, job.id, ...)`) after any runtime post that runs its own transaction: World reads each mutation's result through `commands.result`, and a missing pointer fails there with "Unknown or not yet admitted review: review-ui:...".

Milestones (plan ready, completed/incomplete/failed with confirmed findings) are mailed to the owner through the runtime's ordinary post path on thread review:<id>. Message ids include the job generation, so replay or restart does not duplicate a notice, and a failed notice never changes the review. Scope/accounting checks validate model output; they do not certify that a semantic decomposition or finding is correct. Completed execution, coverage, findings and approval remain separate. Gaps, incomplete questions and requested additional work remain incomplete even with zero findings.

Restart interrupts outstanding attempts and jobs; explicit resume waits for prior program cleanup. Every resume rechecks the planner through the attempt path, including fingerprints of the advisory catalog and resolved model policies. Reusing that exact planner retains the plan revision; a fresh planner advances it and requires fresh inspections. Each planner, focused, integration and validation attempt receives its role fingerprint from the same catalog; the attempt owner checks that binding before reuse or launch. The final catalog check remains necessary for changes elsewhere in the advisory catalog, but matching endpoints alone cannot validate an intervening attempt recorded under another policy. Completed exact-input/current-policy passes can be reused on the same target, while incomplete or validator-challenged passes run with new identities. Record the selected attempt IDs after guarded completion instead of making readers infer coverage from the newest row for a pass. Resume clears current coverage selections while retaining attempt history; a challenge cannot disappear merely because a completed inspection report was reused. Approval must use a stable terminal assessment and its revision: in-flight progress is not a signable frozen result.

Report a review as planned, or a pass as done, only from `review_attempts.state` and `review_jobs.plan`. A reviewer's finish_task mail arrives 1-2.5 minutes before its structured result is recorded; `/reviews` read the records and was right when a report built from mail was not.

Authorized additional work is a revision/digest-bound operation on a settled retained target. Its question, reason and stopping condition enter the next plan as required work; clearing selections advances the assessment without deleting attempts. Admission rechecks generation, owner, state and revision after asynchronous artifact verification. Resume alone does not authorize another question or capture later edits.
