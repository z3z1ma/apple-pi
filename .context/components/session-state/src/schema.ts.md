Forward migrations preserve recorded provenance. The link-origin migration leaves existing links' organization null rather than deriving a historical origin from today's tree; the links reader uses surviving evidence for legacy resolution and explicitly reports unknown ownership when none remains. New links write their organization with their endpoints and recorder in one insert.
Why: a discarded temporary peer can leave artifact-only links with no surviving ownership evidence. Guessing an origin during migration would turn missing history into authorization.

The participation migration (physical version27 to28) seeds surviving participant rows at their known `joined_at` and records the tracking boundary. It does not infer deleted memberships or relabel subject-only mail as escalations.
Why: earlier channel departures deleted their participation rows. Surviving joins provide partial evidence before the boundary, not a complete audience history; readers disclose that limit.
The peer-caller migration (physical version28 to29) preserves surviving `program_peers.created_by` as `program_peer_observed` at migration observation time, never as a birth or zero baseline. Older discarded identities can remain known-temporary without recoverable caller history. Existing transfers stay authoritative and caller events are not overwritten on replay. An observed mapping after prior discarded/unknown identity is still retained as an observation, but cannot establish that identity's earlier lifetime caller. Reader first-fact precedence keeps such ambiguity unknown without inventing eras or treating a missing provisional row as proof of original cleanup.
Why: startup cleanup can erase the last authoritative caller row. Guessing a birth or zero baseline would import historical spend, while using today's reporting manager would change immutable accounting ownership.
The hire-date migration adds nullable `sessions.hired_at` and writes no rows. Existing people, including those with an already applied start, stay null.
Why: a start command that looks like a hire is not proof of when that person was hired. Filling the column from old commands would invent dates the operator chose not to guess.
The specialization migration adds a nullable column without backfilling existing identities. Only first creation supplies the value, including its absence; later reconnect/call-in and failed launch retries keep that original record.
