Registering a workplace tool and making it active are separate steps. Every-person tools belong in `PERSON_TASK_TOOLS` as well as `installWork`; activation restores them on both session start and before an agent turn while preserving unrelated active tools. `link` is a general relationship tool for everyone. `INSIGHT_TOOLS`, including `predictions`, follow the same management capability gate as lifecycle tools (a managing role or unroled recorded root) and are removed from nonmanagers even if a transcript saved them active. `/org` remains a human command regardless of role.
Why: registration alone passes the loader surface check but can leave a tool unavailable to a running person's model after an explicit tool selection or role change. Faux-session calls and coordinator activation tests cover the runtime behavior that the loader alone cannot prove.
Inspection resolves a caller's current organization and scope before invoking the shared reader; the reader owns historical task and holder semantics. `org_work` renders those structured results without deriving a separate classification.
Why: current input authorization and historical observation answer different questions. Replacing the reader's event-time rules with today's roster can rewrite past views.
`org_fitness` keeps a root `Type.Object` with optional window/scenario fields and exactly-one-mode validation in execution. Native Pi Exec signatures inspect root properties; a root union would erase the tool's argument surface. Scenario preview captures one now for all relative origins. `predictions` belongs in the management insight activation set, separately from registration.
Why: a schema that validates direct calls can still become a zero-argument composition signature, and loader registration does not prove role-appropriate activation. Native/faux-session proof does not establish composition-runtime execution.
`/org` is registered here to reuse the native fitness/expertise readers and their rendering, rather than executing model tools without an assistant parent. Its overview captures one cutoff for waits/work/requests and gives `communicationIn` an empty traffic interval: pending requests are independent cutoff snapshots. The command adds no classification, goal-file reads or stored summary. The common expertise selector maps a unique exact roster name to its ID before the existing reader/resolver, for bare and explicit `person:` forms. The roster includes the caller, whose own name the shared address resolver otherwise excludes. Duplicate roster names require an ID even when one match is the caller; passing that collision to the old resolver would silently select the other person. IDs and explicit unknown-person inputs retain the existing reader/resolver behavior, while other full arguments remain areas.
Why: historical traffic is unnecessary for an overview, while a guessed lookback or a second formatter could diverge from the native contracts. Command handler errors are emitted through Pi's extension error channel, not promise rejection from `session.prompt`.
The runtime owns completion retention; this tool only submits the finish command and describes its contract. Updating or reloading the tool does not replace an already-running daemon's implementation.
Why: stable-path retention is enforced in `changeWork`, so testing the registered tool against an isolated newly started runtime proves the new command behavior, not activation in a long-lived installed daemon.
Assignment persistence and waking its recipient have separate failure boundaries. A reported wake failure can leave the assignment and goal bundle saved. Inspect the retained assignment and call in the existing person without a new goal instead of repeating goal creation.
Why: an observed `assign` saved work before reporting that automatic wake needed a tmux pane; `call_in(person)` resumed that saved work. Treating the wake failure as rollback can duplicate the task.
