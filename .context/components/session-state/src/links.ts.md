## file

The vocabulary in `relations.json` is read fresh on every call, and the runtime, not the tool, refuses an unlisted relation. Adding a relation is one line in that file. The `link` tool's description lists the vocabulary as it stood when the session started, so a new word reaches a running session's prompt only after a reload. Recording already works.
Why: the operator wants a defined vocabulary that is easy to extend, with no code beyond the list. Validating in the runtime keeps scripts and programs that send `link_record` directly under the same list.
Only `blocks` and `requires_decision` carry behaviour here: `resolveWaitsOn` ends them when their target task closes `done`, and never on cancellation. Other relations are stored and read. A link's id is its `link_record` command id, so a replay after a restart inserts nothing twice.
Things the runtime records (task, person, thread, message, organization) must exist; commits, PRs, files, and check runs are outside it and taken as named. A new wait on a task already closed `done` is refused, because nothing would ever resolve it. An inferred link must carry a confidence, so a guess never reads as a known fact. Within the authorized organization, who resolves a link (for example a finding's owner) is a convention, not enforced: verification ownership is separate from the organization boundary.
Links stay inside one organization: `recordLink` refuses a task, person, or organization end outside the recorder's root, and `resolveLink` refuses a resolver from another organization. Inside an organization anyone may record or resolve any link.
Why: a security review showed one organization planting waits, with their reasons, in another's views, resolving its links, and seeing its task holders. The enforced boundary covers task, person, and organization endpoints; external artifact names and existing thread/message references are not an additional confidentiality boundary. New links store their originating organization in the same insert as their recorder and endpoints. Resolution follows that anchor's current root, so merges work and deleting a temporary recorder does not destroy ownership or rewrite provenance. The forward migration leaves old rows' organization null; resolution can use surviving endpoints or a surviving recorder for those rows, but refuses with an explicit unknown-organization error when no evidence survives. A cross-organization row written before this rule may show in one organization's views yet belong to the other for resolving; such a wait still ends when its target task closes done.
`WAITS` is the one list of wait relations; fitness reads it for delay states and open waits, so a new wait word is added here only.
