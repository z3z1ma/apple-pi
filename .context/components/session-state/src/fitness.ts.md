`evaluate` is the pure evaluator U: it knows only economic events and a window, never the database, scenarios, or roles. Every event is a point charged when `from <= at < to`, or an interval charged by its overlap, which is what makes any split of a window add up (partition invariance). The history adapter turns recorded facts into events; later a scenario adapter feeds the same evaluator, so realized and expected fitness stay one function.
Why: the spec requires expected fitness to be the same arithmetic as realized fitness; a second calculator for scenarios would drift. An earlier draft charged a task's whole delay at completion, which double-counted delay across windows.
The adapter reads current valuations only for tasks with owned obligation overlap or an owned completion in the requested window (repricing restates history, as the operator ruled). It establishes this relevance before accessing `task.md`; errors in relevant files remain errors. Opens and closes come from runtime records, so archiving a bundle does not change past windows. Tasks without an `opened_at` are not obligations.
Why: pricing all tasks before ownership filtering made an unrelated organization's invalid goal file fail the caller's query. A future adoption or completion is not sufficient relevance for a past window. The adapter's returned valued tasks already are the coverage set, so the consumer needs no second window filter.
Open-wait eligibility is separate from economic relevance: fitness passes all pre-pricing eligible task IDs to the snapshot reader, including tasks closed before the requested window, while keeping temporary-peer-only ephemeral steps out of the task-origin branch. Recorder-based admission still uses active membership. Inspection omits this eligibility filter and examines retained tasks. Neither snapshot path reads goal files.
Why: using valued records as wait candidates erased a surviving wait after its source task was cancelled and its recorder retired; removing eligibility altogether admitted program-internal steps into fitness. Eligibility, pricing relevance, and historical ownership answer different questions.
Task ownership uses the recorded organizational anchor's structural ancestry at the judged moment, ignoring retirement and temporary-person eligibility. Completion uses its timestamp; delay intersects ownership intervals with obligation/state spans and the requested window. Task closes and resolutions have millisecond timestamps, so joins at the same timestamp count; this is not event-sequence precision.
Why: today's root imported pre-join value and delay into past windows; using active-person membership instead would make retirement erase outstanding obligations. Current work authorization in `tree.ts` and present-roster expertise intentionally answer different questions from historical ownership.
`realizedFitness` evaluates any window it is given, and an open task's delay runs to the window's end. The `org_fitness` tool refuses a window ending after now.
Why: a future end would count delay that has not happened as realized; expected fitness for the future belongs to scenarios.
Ephemeral tasks held only by temporary `pi_exec` peers never count, before or after the program discards those peers; the adapter excludes the same set `discardProgramPeople` deletes, so disposal changes no window. A temporary peer's work is a step inside its caller's task, not an obligation of the organization. Its spend belongs to the first lasting creation caller, rather than creating another task obligation. Durable temporary identity is used by both financial eligibility and cleanup; retained ended assignments cannot turn a previously discarded temporary holder into a lasting one during sequential disposal.
Why: counting them while the peers lived and losing them at disposal made the same past window read $45 and then $0 in review.
Compute counts a `cost_changed` increase when the spender's manager chain at that moment reached the organization and the spender was not let go (`retired` until `rehired`). The chain is replayed from the runtime's events in `seq` order: `reports_to_changed` (a hello seeding a manager) and `transferred` (a move); before its first change a person had the manager that change replaced, and a person with none has its current manager throughout. `manager_changes` rows are not read. A cost change marked `hello` (a hello's cost when no cost was ever recorded for the session) is a baseline. A temporary peer's spend maps recursively through immutable caller facts to the first lasting caller and is admitted under that caller's event-time membership exactly once. Reporting moves do not change this accounting beneficiary. Active-person membership still excludes durable temporary identities, while structural ancestry uses retained caller as a missing-row seed and honors subsequent transfers. Unknown callers remain uncharged rather than guessed. Ambiguous/unknown temporary identity has a null initial structural seed, ignoring a reused current snapshot and first-event `from` backprojection; actual recorded `to` changes still apply at their own replay event. This prevents a lasting descendant's older costs from moving organizations through an ambiguous reused parent, while known caller/ordinary seed conventions stay unchanged. Migration observations establish known callers without inventing birth times; new creation writes a zero baseline before hello, so first positive spend is not mistaken for preexisting transcript cost. Spend is placed at the time the runtime observed it; during an outage the bridge keeps only the cumulative total, so the missed spend lands at the reconnect (a convention, not exact spend time). Compute before the `hello` marker existed is unsupported: old first-sight spend has no marker and would count.
Why: joins and moves judged by today's tree rewrote past windows twice in review (a joining root's team brought old spend; a later move dropped real spend), and a join in the same millisecond as earlier spend imported it until the replay followed `seq`. The bridge reports a session's whole transcript spend at its first hello; once a cost is recorded, a reconnect after an outage reports real spend.
A task's delay is cut into spans by state (`delayStates`): waiting while a wait link (`WAITS` in `links.ts`) from it is open, otherwise in progress while it has an open assignment, otherwise queued. The spans cover the delay interval exactly, so the states sum to the delay and windows still add up. Open waits and interruptions describe the window; they never change the total. Every membership judgment uses one `membership` replay: compute and questions resolve their accounting person at their own event, operator mail at its message time, and a wait recorded by a person uses active membership at the window's end. Temporary callers affect only accounting, not generic recorder membership, link admission or person eligibility. Today's tree is never used for history. Operator-mail interruptions include both `mail` and explicit `escalation` kinds, so the native writer's new kind preserves the same attention accounting. Mail messages and the operator's joining a thread carry no event sequence, so they are judged at millisecond resolution: a join, or the operator's arrival, in the same millisecond as a message counts the message (a stated convention, not an ordering guarantee).
Point membership/manager queries replay only structural changes. Replay with a callback still visits the full ordered stream, including cost and prompt facts.
Why: communication asks many point queries; parsing every unrelated cost event for each message produced measured quadratic scaling. Filtering the callback stream instead would silently remove compute and question observations.
Recorded link impacts enter the same evaluator as `link:<id>` events; estimates and findings stay evidence. Impact selection uses impact time, not link creation time: backdated assertions restate past windows, preserving partition invariance even when recorded after a window's end. Impact ownership follows the persisted origin's structural ancestry at impact time, legacy task endpoints then recorder membership only when no origin exists. Finding activity is creation in `[from,to)`, grouped by target task and recorder; resolution uses `resolved_at <= to`, matching snapshot ties. This is not a resolution-activity report or a reviewer score. Subtree filtering changes evidence and explanatory contributions only, never root totals. Impacts are assertions, not verification or avoided-loss credit.
Why: filtering links by creation before reading impact time lost a link recorded at 3h with an impact at 1h from the window [0h,2h), while admitting it to [0h,4h). That made adjacent window totals disagree with their union. Findings intentionally answer a different question: review activity created during the window, with the resolution known at its cutoff.
Dropped-work spend is an annotation of existing evaluated task delay and eligible compute events, never another economic event. Compute follows the economic event's accounting source, so attributed temporary-peer spend uses the lasting caller's focus, not the emitter's separate task. This is the accepted caller-focus explanatory estimate, not emitter-level allocation or another charge. Compute is estimated from retained `work_changes` joined to the runtime's atomically posted `<command_id>:post` task message, replayed before the window too. Equal-time transitions follow message `seq` and transitions at compute observation time are included; there is no shared causal order with cost events. Current cancellation/replacement may postdate the selected window; a supersedes target is the replaced task. Known eligible owned non-dropped focus is attributed, while absent/unknown/foreign/internal focus remains unattributed. Subtree selection uses existing task/person explanatory scope, never a subtotal score.
Why: current `work_focus` would rewrite attribution after a focus switch; all assignments are not focus; charging these explanations again would double-count costs. A successful focus without a retained change/post pair cannot honestly be recovered. `runtime.applyWork` is the production owner of this atomic pair; the test fixture uses `changeWork` and `postToThread`, not a second invented focus log.
A permanent `person_departed` marker retains the last reporting snapshot after removal of the live person row. It supplies only a missing seed; the first recorded transfer's `from` still overrides that snapshot, and subsequent changes apply at their recorded times. The marker ends active membership, not structural ownership of retained tasks or links. Historical `retired`/`rehired` events remain readable as past facts; they are not a current reopening capability.
Why: a hire can receive its manager through the provisional row without a reporting-change event. Deleting that row otherwise erases earlier compute and ownership; using the departure manager without the first-transfer override would instead rewrite earlier reporting.
