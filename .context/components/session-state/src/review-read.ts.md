These are read-only projections over the runtime's review records. Read a consistent SQLite snapshot when combining a job, its selected attempts and their reports. Keep selected completed coverage distinct from the full attempt history: a later failed attempt or a report from another plan is not automatically the current assessment. Finding handles include the actual attempt identity so a new allegation cannot silently inherit a decision attached to an earlier pass with the same local finding ID.

Organization scope follows the review's recorded root through the existing tree; `scopeClause` is the one place that builds it, for both `reviewQueue` and the id/state-only `reviewStates` the Workplace badge polls. Inventory roots from review_jobs, not tree.ts anchorsOf: that helper inventories work_tasks, and a completed review can survive after every temporary task was removed. A whole-root merge without surviving tasks reproduced this distinction. Request-handle lookup follows commands.result, then applies the same review authorization.

Once a review has a plan, `reviewAssessment` always returns a validation: a legacy stored validation (with dispositions and coverage gaps) as it is, otherwise `assessFindings` over the selected reports and the stored duplicate links, if any. Its `attempt` is null when no linking attempt ran (fewer than two findings, or linking failed). An older review that stopped after selecting per-report validators (`validator:<pass>`) but before their merge keeps those validators' dispositions, coverage gaps and limitations over the derived statuses. Findings therefore have a status while passes are still running. An inspection's completed claim does not override a legacy validator's explicit coverage gap. Missing intent stays unassessed; captured intent is not passed intent. Zero findings, validated findings, coverage and execution state are separate observations. These projections do not establish live-checkout freshness or approval. In-flight phase and cost observations can change without a new result revision; a result revision alone is not a live-progress cache key. Queue paging around a selected identity uses the same ordering and scope as the page itself, so a live reorder changes the page offset rather than silently selecting another review.

Cost sums all recorded attempts, not only selected coverage: failed/cancelled turns and earlier plans consumed observed usage too. Reuse refers to an existing attempt rather than charging it twice. Missing, invalid or nonfinite observations are not zero; a nonfinite aggregate is unavailable even when individual observations exist. No attempts is the distinct zero-cost case. These are correlated primary-turn reports, not provider invoices or all internal activity. Keep the observation counts beside the amount.

The cost projection reads JSON text with SQLite's -> operator, then validates the parsed number. Numeric json_extract crosses Node SQLite's safe-integer binding boundary and threw on a recorded 2**53 value; JSON text preserves the producer's JavaScript number semantics and the distinction between numeric and string-valued cost.

Addressed is derived from each assessment (settled, every confirmed finding answered), so hideAddressed filters after ordering in JavaScript rather than in SQL; the queue is small enough that summarizing every review is fine, and state counts stay unfiltered for the strip. The log part reads only the tail of each attempt's transcript (LOG_TAIL_BYTES) because the panels poll it while passes run and reviewer transcripts reach megabytes; it is a display window, not a limit on evidence. Analytics attributes a confirmed finding to the model of the inspection attempt that reported it, and counts every attempt's usage, including failed ones. An attempt without a valid cost observation is counted as unreported, never priced at zero: rows carry `reported` and divide averages by it, and a non-finite sum becomes null, as the summary's cost does. A requested queue page past the end (a filter or shrinking queue) returns the last page that has reviews instead of an empty one; this is the shared cause behind both the TUI and World hide-addressed views.

readReviewSource authorizes and copies the admitted artifact before asynchronous Git work, with no SQLite read transaction held across that work. File inventory and file-line pages use the same explicit paging rules; binary/pointer-only representations have no invented line count. Availability in captured source does not imply independent inspection, whole materialized-copy integrity, or live applicability.

Freshness separately observes the requested comparison, current checkout and policy, with timestamps/errors and no claim of atomicity. It compares Git identities, intent and configuration instead of recapturing: every captured region and file list derives from the trees, and a full recapture took about a minute on this checkout before Git-native capture. Project roles are materialized from the selected head tree as capture's full checkout has them: every entry role loading passes through (linked ancestors, linked role directories, link chains) keeps its mode and link text, and a link leaving the tree stays a link. A first version copied only one hop and reported unchanged chains as changed. The optional explicit store supports the Electron adapter without redirecting reads into ambient state; no database transaction spans source acquisition.

Probing reviews in the live database by hand: write the query to a `/tmp/*.mjs` file, run one tick, then monitor that file (inline `node -e` quoting broke twice). Use single-quoted SQL literals, table-qualified columns in joins (`review_attempts` and `sessions` share `state` and `session_file`), and only real columns: `review_jobs` has no `phase` or digest, so take the digest from `read_review`. Findings are cheapest from `review_attempts.output` (JSON `findings[]`) and `review_jobs.selected_attempts`, where `validator` is the merge. `resolve_finding` takes `<attempt id>:<finding id>` and bumps the revision, so send responses one after another. Per-model cost is `review_attempts.result -> '$.usage.cost.total'` beside the `model` column; model choice dominated review cost (about $4 against $0.63 per pass), more than process changes did. `review_jobs.updated_at` moves on later finding responses, so measure a review's duration as `max(review_attempts.finished_at) - created_at`.

Every already-running Pi session keeps the reader it started with until it restarts or reloads, so a change to a stored output shape must stay readable by the previous reader. When your own session crashes reading new records (`undefined` reading `find`), read with the checkout's code: a `/tmp/*.mjs` script run with `node --import ./components/session-state/src/register.mjs` that imports this module, and answer findings with the `review` command through `client.ts` `sendCommand`.
