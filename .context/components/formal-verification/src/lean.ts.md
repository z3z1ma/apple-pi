The check never edits the user's file: the source is copied to a scratch directory as module `ApplePiChecked` and compiled with `--json -o` (the file's own diagnostics, lines unchanged). After the audit, `leanchecker` replays the module's declarations through the kernel, together with every imported module whose `.olean` lies inside the Lake project and outside `.lake/packages` (from the audit's module list). The toolchain and Lake packages such as Mathlib are trusted: replaying them (`--fresh`) would take far longer, and they are checked upstream.
Why: elaboration can add a declaration without kernel checking (`set_option debug.skipKernelTC true`, or meta code calling `addDecl` under it), so a `theorem bad : False` with an ill-typed proof compiles and audits clean; only the replay catches it. A replay failure that names a declaration is an error; any other failure (for example a toolchain without `leanchecker`) is incomplete, never pass.
An audit file that imports only `Lean` then calls `importModules` on that module inside `#eval` and writes a JSON report (every constant the module added, its kind, whether it was written, and `collectAxioms`) to a random path in the scratch directory.
Why: names, kinds and axioms come from Lean's environment, not from parsing source or text; source scanning missed same-line, `set_option ... in`, string-hidden and namespace-shadowed theorems, and `#print axioms` text could be fooled by a quoted name. The module is not imported in the audit's header because the `lean` frontend runs imported modules' `initialize` blocks, and an initializer could print or exit to forge the audit; `importModules` from `#eval` does not run them. The cost is loading the module's dependencies a second time (about the cost of `import Lean` again).

Listed theorems are theorem constants with declaration ranges (written by the user, including through macros, hygienic or underscore-prefixed names); private names are shown demangled. By default every theorem constant, generated ones included, must use only standard axioms; with `theorems`, only those named, and each must be a theorem of this file with an unambiguous name. Every constant of any kind fails the check if it depends on `sorryAx`, so `set_option warn.sorry false` does not hide sorry. An `example` adds no constant, so a sorry inside one is visible only through the warning.

A standard axiom counts only by name and provenance: its declaring module's `.olean` must lie in the toolchain's `lib/lean` (paths compared after `realpath`). A `prelude` file, or a project module that shadows an `Init` module, can declare its own `propext`; that one is nonstandard.

`pass` requires every process to exit 0 without timing out, no error diagnostic, a clean kernel replay, a valid report naming the module, at least one listed (or requested) theorem, no `sorryAx` anywhere, and the axiom rule above.

elan: an existing `$ELAN_HOME` or `~/.elan` is reused when it has `elan`, `lean`, `lake` and `leanchecker` launchers. Otherwise a pinned elan installs into a unique staging directory beside the cache home and is renamed into place only when complete. Publication holds a lock file beside the home (`<home>.lock`, created exclusively, holding the owner's pid; a lock whose owner is no longer running is removed). Under the lock, a complete home (a concurrent winner) is kept and an incomplete one is renamed aside before the staged install takes its place, so no call ever replaces a complete home. The elan archive is checksummed; toolchains elan downloads are not. A first `lean --version` (untimed, cancellable) installs the toolchain; the deadline starts after it and covers `lake build`, `lake env`, the compile and the audit. In a Lake project (`lakefile.lean` or `lakefile.toml` up the tree) `LEAN_PATH` comes from `lake env` with the scratch directory in front; a `lean-toolchain` alone selects the toolchain; a lone file uses `LEAN_TOOLCHAIN`.
