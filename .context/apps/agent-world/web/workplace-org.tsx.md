## symbol:Org

Org keeps one plan and the actual world snapshot separate. A role position is a proposal, never a person; Start team returns actual session identities that are retained on every retry. Only explicit backend editable=true unlocks a rejected plan: a missing visible person alone cannot prove that no launch/goal/move was recorded.

Closing the plan and profile inspection hide rather than discard it; Resume returns to the same draft ID, person tokens and result. New team explicitly confirms replacement, including that created people/work remain. Started setup prioritizes recovery above immutable fields in the Setup plan disclosure. The shell receives only dirty/started booleans via onPlanChange; it owns World/reload warnings. Open team channel delegates navigation to that same shell.
Why: losing a partial plan's identity strands its safe retry route even though already prepared people remain real.

The Setup plan disclosure changes its React key when setup starts or a preflight rejection makes it editable again. This resets the browser's native open state at that transition while leaving the actual draft and result in Org state.
Why: recovery should become visible when setup starts, and editable fields should reopen after an explicitly editable rejection; ordinary progress updates should preserve the operator's disclosure choice.

Chat/Mail keep this view mounted, while returning to World or reloading clears memory-only drafts. Immediate Add person is a separate ordinary recruit flow, not a one-position team plan. Its busy callback protects parent navigation from unmounting an in-flight request; after an uncertain result the form protects against blind resubmission.

A new position's optional specialization stays in the retained draft and locks with role/goal once startup begins. Retries carry the same whitespace-trimmed creation value, including after a new position receives its actual person ID. Existing teammate specialization is read-only snapshot metadata and is omitted from the start payload, even while staging that person into another team.
Why: specialization describes a focus within a fixed role; reorganization is not permission to change an existing person's identity or responsibilities.

The shared Team task and new-position goals are optional. The renderer omits blank goals and sends only the operator's explicit trimmed text; the backend owns inheritance from a supplied Team task. The UI locks these values once preparation starts, including absent goals.
Why: preparing roles and reporting relationships is useful without assigning work; role mandates and specialization are not permission to create synthetic tasks.

Existing teammates retain their current work: their position-goal field is hidden, their payload omits goal, and the individual-work preview counts only new positions. Existing work remains visible through the usual profile, not copied into a proposed assignment.
Why: the backend's existing-person path moves or wakes that identity but never assigns a new position goal. An editable field would promise an effect that this path does not perform.

A plan without a Team task previews readiness or its explicit new-position assignments. A completed result claims delivery of a shared team task only when the progress result contains kickoff; without kickoff, explicit position goals may still have started individual work. Completion means team setup is ready, never that its tasks are complete.
Why: shared kickoff and individual initial work are separate backend paths, so absence of kickoff alone does not prove that everyone is idle.

Whole-team startup explicitly discloses operator pull membership before submission. Joining is not a read acknowledgment. Runtime remains authority for reporting/work safety; the UI sends the observed lasting branch and never changes the tree optimistically.

Native move confirmation owns focus and Escape; refusal appears inside that active dialog, not only in the inert background. The embedded shared profile resets position to static so narrow-screen profile styling cannot cover reporting controls.
