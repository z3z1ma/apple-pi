One WorkplaceMenuProvider owns the active menu for the renderer. Consumer handlers only request items/coordinates; they do not mount separate menu stores. The portal targets the trigger's enclosing wp-app so light/dark palette variables survive portal placement. The World pointer menu remains separate because it owns game Actions, hover presentation and mouse-leave semantics.

Menu selection/Escape restores a still-connected trigger before the action opens its editor. Outside pointer or focus transfer dismisses without restoring the trigger, preserving the newly chosen control's focus. This includes keyboard-opened Quick Open: its focused input must replace the old menu rather than sit beneath it. Focus moving between the menu's own buttons keeps it open. Pointer contextmenu events use client coordinates. Ordinary clicks anchor to the trigger's left/bottom, including native button clicks generated by Enter/Space whose client coordinates are zero. Keyboard opening consumes only ContextMenu or Shift+F10, anchors to the same trigger and leaves ordinary input alone. A stable open/close callback keeps routine world snapshots from restarting the focus effect. Native buttons implement activation; arrow/Home/End navigation skips disabled items.
Why: names and editor tabs need one coherent keyboard/focus surface without importing game state or creating competing popups. A keyboard shortcut can focus another surface without a pointer event; restoring the menu trigger in that path would steal focus from the newly opened picker. Native button activation can also arrive as a MouseEvent with zero coordinates: treating every MouseEvent as a pointer location would place a keyboard-opened ellipsis menu at the viewport origin rather than beside its control.
