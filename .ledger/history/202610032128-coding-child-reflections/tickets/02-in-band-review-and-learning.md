# 02: Finish coding children with in-band review and learning

**What to build:** Return coding-child handoffs only after their due automatic review and learning work finishes in their own conversation. Use one pre-settle continuation to review/revalidate first, capture worthwhile learnings second, and return the updated full report last. Enable this for active built-in `edit`/`write` capability independently of pairing, without a new opt-out. Reuse existing review lenses and evidence handling, keep any enabling refactor inside this slice, and include runtime guidance, product-contract updates, and behavioral verification at the confirmed SDK seam. Follow the [governing specification](../spec.md); a later TDD invocation still requires fresh seam confirmation. Primary passive forks and excluded workers/internal sessions remain unchanged.

**Blocked by:** 01: Contribute and recall sourced child learnings.

**Status:** done

- [x] When an eligible child has made a successful built-in edit/write and its pre-settle continuation is held open, the interactive-agent result remains pending. After that continuation edits/revalidates and finishes, the returned files and full report reflect its final changes and checks, not the earlier implementation report.
- [x] A child's successful edits to tests, other code/non-prose, and prose receive the applicable existing review lenses and execution evidence after each last change. A completed eligible invocation without successful built-in edits/writes receives learning reflection without a change-review task; recording no worthwhile learning remains a valid result.
- [x] A custom child with active built-in editing capability receives the automatic phase with `pair: false`, without relying on a coding role name or inference profile. In a session's initial invocation and subsequent resume, each due hook is scheduled once; review edits do not cause another automatic review. An ineligible child receives no coding completion phase.
- [x] When both activities are due, one boundary continuation instructs review/revalidation, learning capture, and the full final handoff, without a mandatory separate model request solely for learning. Successful notebook additions made in that phase appear in the primary notebook through ticket 01's contribution path.
- [x] Stopping an invocation during its automatic phase, navigating/shutting down its owner, or reaching its ordinary configured turn ceiling stops reflection through the normal child lifecycle. Available work is retained and any returned handoff identifies unfinished reflection without claiming reviewed success; no detached reflection continues to edit files afterward.
- [x] An automatic model continuation that fails after Pi's normal retries yields an ordinary failed-child outcome, retaining available work/report/evidence rather than returning the earlier report as reviewed success. When a notebook addition alone is rejected or cannot be committed but coding/review succeed, the successful full handoff identifies the uncaptured learning and reason.
- [x] When automatic review finds ambiguous intent, the child uses available `clarify` advice; if existing parent context cannot resolve the question, it leaves the disputed change alone and returns the question and affected verification explicitly. The updated full result also includes review status, validation outcomes/gaps, and a brief learning summary, with no extra hook-specific root notification.
