# 11: Teach the fitness loop

Part of the approved spec [../spec.md](../spec.md); its Terms table defines obligation, completion, window, horizon, and the other words used here.

**What to build:** People learn the loop from their prompts and the docs. The `<manager>` charter teaches: value every task you create or assign, never count the same value twice (by splitting work, or by valuing a fix that only restores value already credited); record the damage a defect actually caused as an incurred impact, and never an avoided loss; record links when work waits, produces, verifies, supersedes, or fixes a defect in completed work; read fitness in the sweep; compare candidate organizations by writing scenarios from the same decision point and starting work state, on the same opportunities, valuations, and horizon, in which every role counts only through how it changes outcomes (losses, dropped work, delay, which work is chosen), with accepted findings and the organization's history linked as evidence; mutate with the existing tools, or deliberately keep the organization stable so people keep building context; record the scenario as a `predicts` link before making the change, then report the change with its diagnosis, actions, and expected fitness; advising roles record findings with `finds`; look at the prediction later. It replaces the current rule to hire a manager when fan-in would make you the bottleneck with guidance ("when fan-in repeatedly constrains progress, consider whether changing authority, assignments, or reporting would improve expected fitness"), and carries the brief's principles without fixed thresholds: cheapest change first is not a rule; restraint is valid; reporting manager, task owner, and decision authority are separate roles that may coincide; loosely coupled work suits parallel people while tightly coupled work suits one strong owner, and riskier work adds an independent challenger. The `<org>` section names `fitness` and `predictions`. `docs/session-state.md` describes the fitness and predictions contract; `docs/organization.md`, `docs/boundaries.md` (links are neither a hand-off record nor work records beyond tasks), and the README catalog match.

**Blocked by:** 06 (Delay by state, open waits, and operator interruptions), 07 (Impacts, defects, and review findings), 08 (Spend on dropped work), 09 (Scenarios and recorded predictions).

**Status:** ready-for-agent

- [ ] A manager's system prompt contains the loop (including writing scenarios and that roles count only through outcomes), the value-conservation rule, the report contents (diagnosis, actions, predicted fitness), the fan-in guidance, and each listed principle; it no longer contains the rule to hire a manager when fan-in would make it the bottleneck.
- [ ] Every root session's `<org>` section names `link`, `fitness`, and `predictions`.
