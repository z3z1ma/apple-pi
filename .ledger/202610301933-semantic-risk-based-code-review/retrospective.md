# Retrospective

## What mattered

The operator's correction changed the inquiry from a fresh whole-diff reviewer to semantic scope, risk-directed depth and durable artifact-bound results. The proposal keeps the simple reviewer as an evaluation baseline without letting it restrict the requested design.

Direct source tracing changed what could safely be borrowed. Open Code Review's grouping model sees file metadata, not changed code. PR-AF's inspected dimension cap uses the original depth despite an effective-depth assignment, and file-set dedup can merge distinct questions. roboRev persists dirty patch text, while the inspected dirty worker path can still use a mutable checkout. These are bounded source findings, not judgments of overall review quality.

The local ownership trace mattered just as much: a foreground pi_exec connection owns its temporary people. A durable review queue therefore needs an explicit runtime job owner; merely backgrounding a program would not satisfy the requested continuity.

## Evidence and limits

The root verified decisive source paths at pinned revisions and wrote the complete proposal. A scientific-skeptic independently checked the claims and found no material contradiction; a cold reader reconstructed the decision and found no material comprehension gap. Both finished and were sent home after idle/zero-assignment checks. Neither result establishes implementation safety or effectiveness.

The proposal names deterministic obligations separately from probabilistic semantic completeness. It also keeps completed review, accepted risk, optional human approval and applicability to current code separate. No reference engine, production test suite, new runtime or comparative model experiment ran in this task.

The operator approved the plan with notes and those notes were applied. He rejected custom sandboxing/environment limits as unnecessary complexity and said `/work` is going away, while welcoming a review-focused replacement. The revised plan uses ordinary advisory-role peers and a dedicated `/reviews` interface plus Workplace Code. Source capture remains for accuracy, not confinement. This removes work rather than moving it to a later phase. No implementation is authorized by the current task.

My draft had made a helpful reproducibility mechanism into a new capability-restriction project. The correction was to keep the concrete target/receipt guarantees and use the environment the harness already provides. Existing UI extension points are also not automatically the right product surface when the operator does not use them.

## Improvements owned by the proposal

- Check captured-source fidelity and normal reads from the review directory after live-source mutation; use ordinary tools without a new confinement layer.
- Prove first-request isolation after actual startup/mail replay, rather than infer independence from new session IDs.
- Prove durable attempt fencing across disconnect/restart/late-result paths before treating the queue as reliable.
- Evaluate semantic/risk-directed review against the simple baseline with confirmed defects, false positives, triage effort and actual cost. Agree resource allowance and decision tolerances before comparative execution.

These are acceptance checks for later authorized implementation, not completed experiments or new unrelated tasks.
