# Session state

Apple-pi keeps one shared account of your Pi sessions in a SQLite database. Every root Pi session reports to it, and every view reads from it. The design and the remaining steps are in the ledger task `.ledger/202610172354-session-state-model/` (`spec.md` and `tickets/`); this page describes what exists now.

## Parts

- **Bridge** (`components/session-state/src/bridge.ts`, loaded by `extensions/session-state.ts`): an extension in every root session, including the temporary peers of `pi_exec` programs; the internal `/btw` session does not load it. It reports the session's identity, its process, and its run state, sends a heartbeat every second, and reports a clean shutdown.
- **Runtime** (`components/session-state/src/runtime.ts`): one daemon per Mac and the only writer to the database. The first bridge that finds no runtime starts it with `node`, detached, and it keeps running after sessions end. One instance is guarded by an exclusive SQLite lock it holds for its whole life; the operating system releases it however the runtime exits, so there is no stale lock to clean up. If the runtime cannot start, the session shows one warning naming the runtime log.
- **Clients** (`client.ts`): `sendCommand` sends one command over the socket and starts the runtime when none answers; the workplace tools, `scripts/pi-send.mjs`, and Agent World use it; the close notice goes over the bridge's own connection. Mail delivery and the mail tools live in `mail.ts`, threads in `threads.ts`, team channels in `channels.ts`, meetings in `meetings.ts`, and assignments and ephemeral tasks in `work.ts` and `work-tools.ts`. `program-client.ts` and `program-peers.ts` connect `pi_exec` programs to their peers.
- **Database**: SQLite in WAL mode, created and upgraded by forward migrations (`schema.ts`; the schema version is SQLite's `user_version`).

Everything lives under `~/.pi/agent/state/` (or `$PI_CODING_AGENT_DIR/state/`, where a leading `~` means the home directory, as in Pi): `apple-pi.db`, the socket `apple-pi.sock` (mode `0600`), the lock `apple-pi-runtime.lock`, the running runtime's pid in `apple-pi-runtime.pid`, and its output in `apple-pi-runtime.log`.

## What it records

- `sessions`: one row per Pi session id, with its kind, session file, directory, name, current run state (`idle`, `thinking`, `writing_reply`, `running_tool`, `compacting`), and current generation, plus everything else its bridge observes:
  - the top-level tool running now (`current_tool`, its id, its main argument such as the command or path, and since when). Pi can run several tools at once: each start and end is an event with its duration, and while any still runs, the session shows the most recently started one;
  - an open `prompt` (JSON): a questionnaire with its `id` and questions while `ask_user_question` runs, or another dialog's kind and title;
  - the `queue` (JSON): steers and follow-ups typed during a run and not yet delivered (Pi delivers steers first), and `pending`, Pi's own flag that something waits, which also covers messages other extensions queued;
  - `last_error` (a failed reply's message) and `last_abort_at`;
  - `model`, `thinking_level`, `context_tokens`, `context_window`, and `cost` so far;
  - relations: `reports_to` (the manager session from `--reports-to`), `role` (the role catalog name the session took at its first start, see [Roles](#roles)), `soul` (one line of the soul drawn with the role), `self` (the person's self, its four fields as `##` sections, reported at every start and after each `update_self` in a reflection), `parent_session_file` and `parent_session_id` (the session it was forked or cloned from), and `previous_session` with `previous_session_id` (the session that ran before it in the same process and pane, and whether it gave way to a new session, a resume, or a fork); the ids are filled in once that session is known;
  - `git` (JSON): repository, worktree, and branch of its directory, read when it starts, after each shell command, and when a run settles; null when git says it is not a repository; a failed read (no git, a timeout) keeps the last known value;
  - `config` (JSON): name, the names of the options on Pi's command line (not their values, which could include a prompt), active tools, extensions, loaded skills, and MCP servers. Extensions are the files that registered tools or extension commands; Pi lists no extensions, so one that registers only hooks does not appear.

  Bridges report only `root` sessions. An older database can still hold rows of kind `child`. The runtime keeps them, but never gives them attention, and the directory, team channels, assignments, and views read only `root` rows.

  Only the session's current generation changes these. Streamed text and tool progress update nothing, so they write no events (subscribed clients see streamed text live; see [Live replies](#live-replies)).
- `incarnations`: one row per process lifetime of a session (generation 1, 2, ... on each reopen), with pid, process start time, process state, start and end, and why it ended. An incarnation running in tmux is bound to its pane: the server socket and pane id the bridge reads from `TMUX` and `TMUX_PANE`, and the pane's tty once the runtime has seen the pane (recorded with `tmux` as its source).
- `tmux_servers`, `tmux_sessions`, `tmux_windows`, `tmux_window_links`, `tmux_panes`: every live tmux server (keyed by its resolved socket path, so `/tmp` and `/private/tmp` are one server) and its sessions, windows, and panes, including panes that run no Pi. A window can be linked into several sessions, so each link (session, window, index in that session) is its own row. tmux ids such as `%3` are only unique within a server, so every row also carries the socket. A pane row holds its window, tty, first process, current command and path, and whether it is active or dead.
- `messages`: an index of each session's completed conversation, one row per message (user, assistant, tool result, or an extension's custom message such as delivered mail) and one per tool call inside an assistant message (`part` is the tool call id). A row holds the transcript entry id, the entry's own time (`at`), when the runtime first indexed it (`observed_at`), role, tool, size, and a short preview; the text itself stays in Pi's session JSONL. The bridge looks for new transcript entries after each turn and once a second, so messages appended while the session is idle are indexed too.
- `threads`, `thread_participants`, `thread_messages`: every thread (id, kind `mail`, `escalation`, `channel`, `meeting`, or `task`, subject, creator, when it was created and closed), each current participant (a session id or `operator`, `push` or `pull` delivery, `read_up_to`, and whether it was invited), and each message in order (`seq`). The native `escalate` tool creates the explicit `escalation` kind with ordinary mail delivery; old mail whose subject happens to be `Escalation` is not reclassified. See [Mail and threads](#mail-and-threads).
- `work_tasks`, `assignments`, `work_focus`, `work_changes`: each task (id, bundle path, project, organization, whether it is ephemeral, its `task:<id>` thread, when it became the organization's obligation (`opened_at`), and when and how it closed (`archived_at`, `close_status` `done` or `cancelled`)), each assignment (person, task, assigned by, assigned at, ended at, outcome, and why it ended: `finished` or `unassigned`), one focus per person, and command recovery records. The goal stays in `task.md`, not the database. The `current_task` and `intent` columns and the `session_tasks` table stay in the schema, but nothing reads or writes them. Task tools retain callers and assignees in the task thread's participants, including ledger creation and status callers without assignments; participant IDs are Pi session IDs. Assignments distinguish work ownership from thread participation. Editing ledger files does not assign or focus work. Other explicit relationships belong in `links`. See [Tasks and assignments](#tasks-and-assignments).
- `links`: relationships between things, each with a relation from the vocabulary in `components/session-state/src/relations.json` (one word and its meaning per line; adding a relation is adding a line), both ends as a kind (`task`, `person`, `thread`, `message`, `commit`, `pr`, `file`, `check`, `organization`) and an id, a reason, optional JSON data, who recorded it, whether it was inferred and with what confidence, when it was created, and when and how it was resolved. The runtime refuses task, person, or organization endpoints outside the recorder's organization, and resolutions from another organization. New links retain their originating organization separately from their recorder; resolution follows that organization's current root after a merge, even after a temporary recorder is discarded. Old links use surviving endpoint or recorder evidence; those with no recoverable organization refuse manual resolution explicitly. Pre-rule cross-organization rows are not removed from historical views. A wait (`blocks`, `requires_decision`) on a task resolves when the task closes `done`, never when it is cancelled; every other link is resolved by hand. Readers check that the table exists, since a running runtime may predate it.
- `program_scopes`, `program_peers`: each running `pi_exec` program and the temporary peers it started, with each peer's task, pane or process, and creator. Discarding a peer deletes its row with its session record, assignments, and thread memberships.
- `events`: an append-only history of thread audience joins/leaves (committed atomically with participation changes), the start of complete participation tracking, run-state changes, tools starting and ending (with duration), prompts opening and closing, every other change to a session's facts (`<column>_changed`; a hello's `cost_changed` carries `hello: true` when no cost was recorded for the session before, because it is spend the transcript already held, not new spend), a former member started again (`rehired`), each newly indexed message (`message`), process-state changes, incarnations starting and ending, failed process checks, every tmux server, session, window, window link, and pane added, changed, or removed, and failed tmux reads. Every row names its source (`bridge`, `runtime`, `tmux`, or `migration`) and time. Migration28 seeds surviving thread participants at their known join times and records when complete participation tracking began; already-deleted audiences cannot be recovered. The communication reader reports this boundary rather than presenting earlier counts as complete.

## tmux

Once a second the runtime runs one `tmux list-panes -a` against every server socket in tmux's own socket directory (`$TMUX_TMPDIR`, or `/tmp`, then `tmux-<uid>`) and every socket a live session reported, and brings the tmux tables up to date in one transaction. A server outside that directory with no Pi session in it is not seen; finding it would mean inspecting every process's open sockets.

Each read has one second to answer. Only tmux's own "no server running" or "error connecting ... (No such file or directory | Connection refused)" means a server is gone and removes its rows. Any other failure (a timeout, a server that stopped answering, no permission, no tmux) proves nothing: the server keeps its rows, one `tmux_server_read_failed` event is recorded and logged, and the other servers are read as usual.

The pane's tty comes from tmux, not from the bridge, so the runtime fills it in from the topology and records it with source `tmux` and its own event.

## Commands

Any client can ask a session to do something by sending `{"type": "command", "commandId": ..., "sessionId": ..., "command": {...}}` on the socket; add `"generation"` to bind it to one incarnation, so it can never reach a later one. Commands:

| `kind` | Fields | Effect |
| --- | --- | --- |
| `talk` | `text` | A new user turn; fails with `busy` while a run is active |
| `steer` | `text` | Redirects the active run at its next boundary (starts a turn when idle) |
| `follow_up` | `text` | Queued until the active run ends |
| `abort` | | Stops the active run; applied once the run has stopped |
| `rename` | `name` | Renames the session |
| `set_model` | `provider`, `id` | Switches model; fails for an unknown or unavailable model |
| `set_thinking` | `level` | Sets the thinking level |
| `answer` | `questionnaire`, `replies` | Answers the open questionnaire with that prompt `id`: one reply per question, in order, either `{"selected": [labels]}` or `{"custom": text}`. The dialog in the terminal closes, and the tool returns what the terminal would for the same choices. Fails when the terminal answered first or the replies do not fit; other dialogs are answered only in the terminal |
| `mail` | `from`, `body`, `sentAt`; thread mail also `thread`, `subject`, `seq`, `fromName` | Mails the session; see [Mail and threads](#mail-and-threads). Waits while the session is not running |
| `thread_post` | `thread`, `body`; a new thread also `subject`, `to`, optional `cc` | Posts from the request's session to a thread, creating it when new; applied by the runtime, which pushes it as `mail` to each pushed participant; see [Mail and threads](#mail-and-threads) |
| `thread_read` | `thread`, `seq` | The session has read the thread up to `seq` (applied by the runtime) |
| `run_turn` | `task`, optional `outputSchema`, `contextFile` | Waits until the session is idle, runs one turn, and returns its reply on the receipt. `pi_exec` uses it for peers |
| `cancel_turn` | `turn` | Cancels one `run_turn` request, queued or running |
| `discard_peer` | | Stops a temporary peer owned by the sending program and deletes its record |
| `start` | `tmux` (`socket`, `pane`), `cwd`, `name`, `reportsTo`, `role`, `goal` (`text`, `by`, `title`, `value`, `cost_of_delay`), `prompt` | Opens a tmux window after that pane. A new role hire requires a written goal, saved and assigned before Pi starts. Reopening preserves the stored name, role, and work; a new goal adds an assignment and focuses it. Pi gets the role flag and an instruction to begin its focused task. Fails when the session runs; `delivered` once the window opened, `applied` when its bridge connects, `failed` when the window closes first |
| `work` | `cwd`, `action` (`take`, `assign`, `unassign`, `focus`, `finish`, `promote`), action-specific fields, optional `tmux` | Takes, assigns, unassigns, focuses, finishes, or promotes a task; the task change, thread post, and notifications commit together. An assignment to a person at home calls it in beside the sender's pane, or beside `tmux` for the operator; see [Tasks and assignments](#tasks-and-assignments) |
| `transfer` | `manager`, `by` | Moves the person under another manager; see [Manager tools](#manager-tools) |
| `retire` | `reason`, optional `by` | Asks for a handover, then records that the person left and closes it; see [Manager tools](#manager-tools) |
| `link_record` | `from`, `to` (`kind`, `id`), `relation`, optional `reason`, `data`, `inferred`, `confidence` | Records a link from the sending session; its id is the command id. Refused for a relation not in the vocabulary or a task the runtime does not know |
| `link_resolve` | `id`, optional `resolution` | Resolves a link once, with an optional word such as `accepted` or `rejected` |
| `task_opened` | `bundle` | Records a new ledger task as the sending session's organization's obligation, assigned or not |
| `task_moved` | `from`, `to`, `status` | Records that the ledger closed the task (`done` or `cancelled`) and updates its bundle path, preserving assignments, focus, and thread; a task the runtime never recorded opens and closes now |
| `close` | | Stops a running turn and quits the session's Pi process |
| `mark_seen` | | The operator saw the session (applied by the runtime); see [Attention](#attention) |
| `set_preference` | `key`, `value` (JSON) | Stores a UI preference in the `preferences` table (applied by the runtime; `sessionId` only names the sender, such as `notch`); the notch keeps its choices under `notch` |

The runtime stores each command in `commands` and answers the sender with one `{"type": "receipt", "commandId": ..., "stage": ..., "reason"?: ...}` line per stage: `accepted` (stored), `delivered` (the session's bridge has it), `applied` (Pi took it), or `failed` with a reason. Each stage is also an event (`command_accepted`, ...). No receipt says the work is done; its effects appear as ordinary observed facts and events. A command for a session with no live incarnation, or bound to one that is no longer current, fails at once with `not running`. Sending the same `commandId` again applies nothing and answers with the stage the first one reached. A command handed to a bridge is bound to that incarnation, and only it can report on the command; if the bridge disconnects first, the command fails, since nobody can say whether it was applied (mail is sent again instead). `talk`, `steer`, and `follow_up` fail with `no model selected` when the session has no model. Anyone who can open the socket, which is only your user, can send commands; confirmations belong to the view that sends them.

## Mail and threads

Every exchange between people is a **thread**: a subject, its participants, and its messages in order, stored in `threads`, `thread_participants`, and `thread_messages`. A participant is a session id (or the operator) and is either **pushed** each new message, which arrives as mail, or **pulls** it, reading the thread when it chooses. Each participant's `read_up_to` marks the last message it has read: a pushed message counts as read once the receiver's transcript records it, and `read_thread` marks the rest.

People read and write threads with these tools:

- `send_mail` (`to`, optional `cc`, `subject`, `body`) starts a thread. Addresses are names in the sender's organization, session ids, `my-team` (the sender's reports, or its teammates under the same manager when it has none), `my-manager`, or `operator`.
- `reply` (`thread`, `body`) answers everyone in a thread.
- `inbox` lists the threads the caller is in that have messages it has not read (every thread with `all: true`), with the count and the latest message.
- `read_thread` reads a thread in full and marks it read.

Each sends a `thread_post` command (from the sender's session, with the thread id the tool chose, and for a new thread its subject and recipients) or reads the database read-only. The runtime stores the message and pushes it as one `mail` command per pushed participant, carrying the thread, subject, and sender's name; the receiver reads it as `<mail thread="..." subject="..." from="Name (id)" ts="...">`, at the next safe boundary during a run, as a new turn while idle, or with the first run after it next opens. The receipt's reason names who is asleep, whose mail waits.

Anything outside Pi uses the packaged script, which sends one plain `mail` command with no thread; its path is in the `send_mail` tool guidance:

```bash
node components/session-state/scripts/pi-send.mjs coordinator --from launchd "Tick."
echo "Nightly sweep finished." | node components/session-state/scripts/pi-send.mjs coordinator
```

Both send a `mail` command over the socket, starting the runtime when none runs, and both say when the session is not running (or no session with that id has run yet) and the mail waits. Mail is the one command that waits instead of failing: the runtime sends every mail not yet delivered to each new bridge of its session. The `mail` view lists each mail with `sender`, `receiver`, `body`, `sent_at`, and `delivered_at`.

The bridge hands each mail to Pi as a steer: an idle session starts a turn with it, and a running one takes it at its next boundary (after the current model reply and its tool calls, before the next request). The bridge sets Pi's steering to drain every queued message at that boundary, not one per request (Pi's default), so mail that piled up during a long run arrives together in one request.

A mail is delivered when the session's transcript records it on disk, as a `custom_message` entry with the mail in `details` (Pi writes a new session's file once it holds a user or assistant message); until then a crash or a closed process means it is sent again on the next open, and its id identifies the repeat. A mail recorded on a branch that `/tree` left is not delivered again. When Pi itself starts, mail that waited for it rides the first run instead of starting one (mail sent after it started starts a turn as usual), because the command may carry its own prompt (`pi -p "..."`, `pi --session-id w-7f3a "brief"`) and Pi rejects a prompt while a turn is running. If you press Escape while mail is queued, Pi discards the queue; the mail comes again on the session's next open.

For a stable address, start a session with a fixed id: `pi --session-id coordinator` reopens the same session every time. `/fork` and `/clone` create a new session id; `/tree` keeps it. Session ids are shared across projects, so give a named id such as `coordinator` to one project only.

Mail bound to one incarnation (`generation`) never waits for a later one. A session started with `--reports-to <id>` mails that session in a new thread when it closes, except on reload, through its own connection to the runtime (dropped, with a line on stderr, when the runtime is unreachable, so shutdown goes on): `Session "<name>" closed (<reason>) while <idle|busy|waiting>. Directory: <cwd>`.

## Attention

The runtime keeps, per session, `seen_at` (when the operator last saw it), `settled_at` (when its run last settled), and `needs_you_since`: set when a run settles or a prompt opens, cleared when the operator sees it and no prompt is open, or when the prompt closes with no unseen settle. A run that settles counts (a compaction outside a run does not). A new run does not clear it: a session that mail or a reminder started again still has the result you did not see. Every view shows what the session does now first (asking you, then working, then done and unseen, then idle) and marks a working session's unseen result beside its state. Only `root` rows get `needs_you_since`. A temporary program peer's settled reply goes to its program, so its settle does not need you; its open questions do. A session is seen when a tmux client shows its pane (the runtime reads `list-clients` with its once-a-second tmux poll; no hook) after it settled and when a client sends `mark_seen`; each is a `seen` event. For each tmux server the runtime writes the status-line summary of the live top-level sessions in its panes to `@pi_agents` (asking you, done and unseen, working, idle) and the pane that has needed you longest to `@pi_jump_target`, only when they change, and redraws the status line of every client.

## Roles

A root session started with `pi --role <name>` takes that role for life. A role is a Markdown file in the role catalog (`components/organization/src/roles.ts`): the package's `roles/` directory, then `~/.pi/agent/roles/`, then `<cwd>/.pi/roles/`, a later file replacing an earlier one of the same name. Its front matter gives `title`, `mandate` (one line a manager hires by), `models` (`provider/id` in order of preference), `thinking`, `writes` (whether the session keeps the built-in `edit` and `write` tools), and `manages` (whether it gets management, organizational insights and peer delegation); its body is the role's obligation, which becomes the `<role>` section of the system prompt. At every start the session switches to the first listed model the registry knows, at the role's thinking level, and warns once when none is available; with `writes: false` it drops `edit` and `write` before each run (Pi restores the tool set from the transcript, so posture is re-applied). The role is recorded as an `organization-role` custom entry in the session's own transcript at its first start, so a reopen or resume re-applies it without the flag, and a stored role wins over a later flag. The bridge reports it as the `role` fact. The first start with a role also draws the person's soul: three random Wikipedia articles (`soul.ts`), fetched with no model call, stored in the same transcript entry, rendered unexplained under the role body, and reported as the `soul` fact (their titles), which the directory shows; a failed draw warns and is retried at the next start. Two people in one role differ by soul; a session without a role has none. A role file with a missing or malformed field is reported by path and skipped, and an unknown role name warns and leaves the session unroled. The package catalog holds thirty-two roles, two of them managing (`coordinator`, `director-of-engineering`), each with the minds and mandate listed in [the organization](organization.md); whoever holds the manager tools sees the whole catalog, one line per role (name, title, mandate, posture), in a `<role-catalog>` prompt section.

## The organization

Root sessions form organizations: a session started with `--reports-to <id>` has that session as its manager, a session with no manager is a root, and an organization is a root with every session whose chain of managers reaches it, at any depth, at work or at home. The organization is read from the `reports_to` column (`components/organization/src/directory.ts`); nothing else stores it. The runtime owns the tree: a session's `--reports-to` flag seeds its manager at its first hello and is ignored once the record holds one (a bridge started with a stale flag is told its recorded manager), a reopen keeps the recorded manager, and `move` (below) is the only way to change it. Every change is a row of `manager_changes` (from, to, by, when). Prompt identity and mail addressing use that current relationship, not the launch flag; Pi appends prompt changes as structured section deltas. `directory` is the directory of the caller's organization: the operator first, then one line per member (including the caller) with its name, id, title, manager, status (`working`, `idle`, `asking the operator`, or `at home`), availability (`available` or `assigned`), focus, and how many tasks it holds and has finished. `person` (a name or id) shows one member in full: role, team channel, directory, soul, held tasks, the record of finished assignments with their outcomes, and when it first started. The tool result's details keep the whole structured projection for programs and views. A manager also sees the backlog: unassigned live ledger bundles in the `.ledger/` directories of its members' working directories and their parents. `former: true` adds former members with when and why they left. Sessions in other organizations are not listed; mail by id reaches any session on the machine. `/pi-sessions` still lists every live session for the operator.

Every root session's system prompt has an `<org>` section (`charters.ts`): who the session is (name and role title), its id as its mail address, its manager and root, how the directory and mail work, and the tree's norms (work, reports, and escalation follow the tree; a manager is never a relay; say what you verified and what you believe). A hired session is told to ask its manager for people it lacks and when to escalate; an unroled recorded root gets all management capabilities, the role catalog and concise usage guidance while retaining its model, thinking and normal coding posture. A nonmanaging role stays restricted even at the root. A session whose role manages also gets the `<manager>` charter: memory on disk, hiring colliding perspectives from the catalog, giving independent thinkers the problem before the preferred answer, routing by affinity, delegating whole outcomes, naming disagreements, escalating by uncertainty times consequence, sizing from observed demand and capacity, investigating recurring fan-in before changing authority, assignments or reporting, reconciling against the directory, and sweeping. Adaptation can happen during requests, planning, implementation or arriving updates as well as sweeps; important reasoning is recorded and consequential choices revisited. Fitness/scenarios are optional instruments, and deliberate stability is a valid judgment. Its principal is the operator for a root and its manager for a hired manager.

## Organizational inspection

The agent-facing inspection tools and `predictions` are active for managing roles and unroled organization roots. Everyone keeps general task links and ordinary `pi_exec` composition; peer creation and attachment use that same capability gate. The human `/org` command remains available in every root session.

The read-only inspection module (`components/session-state/src/inspect.ts`) derives observations from retained facts rather than storing summaries or deciding interventions:

- `org_waits` reads links, task ownership and assignment/history replay to group open blockers by target.
- `org_work` reads task lifecycle, assignments and open links to show ready, held and waiting work at a cutoff.
- `org_communication` reads thread messages and historical audiences for traffic, and links/explicit escalation threads for pending-request snapshots. Counts do not prove delivery or reading; missing older audience history remains disclosed.
- `org_expertise` reads indexed read/edit/write calls and the current roster for relevant experience, including failed attempts rather than certified skill.
- `org_fitness` uses the existing fitness evaluator over retained economic/lifecycle events and current task-file valuations. Optional scenario comparisons use that same evaluator, not a separate optimizer; coverage and measurement limits remain visible.

`/org` is a compact operator entrypoint to these readers, with fitness and expertise detail modes. Links connect existing tasks, people and evidence; goals and ownership remain task/assignment records. See [the organization](organization.md#workplace-tools) for tool arguments and historical conventions. The harness supplies observations; agents investigate causes and act with existing tools or choose stability.

## The operator and escalation

`directory` includes the human operator at the top of each organization. Anyone can address `send_mail` to `operator`. `escalate(body)` starts a mail thread with the subject `Escalation` to the caller's manager, or to the operator at the root; it returns after the message is stored, so work can continue. `ask_user_question` remains the way to interrupt the operator immediately.

The operator is an address, not a synthetic Pi session. Unread messages in their threads are their needs-you state. Agent World's Mail tab has **Your inbox**, and the terminal sidebar has **Mail** (`m`): each shows the unread conversations, opens them in full, and sends replies to every participant through the thread. Reading acknowledges only the displayed messages; later arrivals remain unread. The normal mail traffic view still shows delivery to sessions and messages from outside scripts.

## Team channels

Each manager has a `team:<manager-id>` thread for the manager and its direct reports. `directory` shows a person's team channel; `inbox(all: true)` lists the channels they belong to. Use `post(channel, body)` and `read_thread(thread)` to share and read context. Normal posts are pulled: they appear unread without starting a turn. A complete participant name or id in a post (optionally prefixed with `@`) pushes just that post to that person. Substrings of another name or word do not count.

`post` can also take `invite`, an array of names or ids. An existing member can invite a colleague from another team as a reader. Invitations survive a reporting-line change; ordinary team membership follows moves immediately. Former members leave the channels; members at home stay. Replies in channels have the same pull-and-mention behavior as posts.

## Meetings

Managers use `meet(people, agenda)` to start a meeting thread. The agenda and each `reply` are pushed to every participant, including the organizer. The organizer decides how long to discuss; there is no round limit. Only that organizer can call `end_meeting(thread, summary)`, which sends the conclusion and closes the thread. Further replies are refused.

Thread messages, meeting closure, and outgoing deliveries commit together before mail reaches a session. On restart, the runtime finishes posts it had accepted and replays the durable outgoing mail without adding duplicate messages.

## Tasks and assignments

Only an assignment binds work to a person. The task tools (`take_task`, `focus`, `finish_task`, `promote_task`, and the managers' `assign` and `unassign`) send one `work` command each. The runtime applies it in one transaction: the assignment or focus change, the file change, a message in the task's thread, and the notifications. A caught failure rolls the files back too. The tools need a trusted project.

- `take_task` or `assign` with `goal` creates an ephemeral task: a bundle at `<state>/tasks/<id>/` with `task.md` (`Status: in-progress`, the goal under `## Intent`, and `## Outcome`) and `retrospective.md`. With `task`, they use a registered task by id, or a live ledger bundle by path or ledger id, and register it on first use.
- A goal may carry `value` (dollars) and `cost_of_delay` (dollars per hour) on `take_task`, `assign`, `hire`, `call_in`, and `rehire`. They are written into the new `task.md` header as `Value: $50 (estimated by Name)` and `Cost of delay: $5/hour`; a value without the mark is unattributed, and the operator corrects either line by editing the file. `readValuation` (`valuation.ts`) reads them back: a missing or unreadable `Value:` is unvalued (not $0), a missing cost of delay is 0, and `/day` is converted to hours. Assigning an existing task leaves its file alone.
- The task's thread, `task:<id>`, has the assignee and the assigner as pushed participants. `take_task` adds the person's manager. Task changes notify the other participants, never the actor itself; the task thread still records the actor's change.
- Each assignment or focus sets the person's focus. A task tool returns the caller's focused `task.md`, its path, and its thread in its result; an assignment from someone else delivers the assignee's goal through mail. The goal is appended again after each compaction. The file is the goal; editing it and calling `focus` brings the edit into context.
- `finish_task(outcome)` adds an `### Assignment <n>: <name>` section with the outcome to `task.md`, ends the focused assignment as `finished`, clears focus, and posts the outcome in the task's thread. When no assignment of an ephemeral task is still open, the runtime sets `Status: done` and moves the bundle to `<state>/tasks/history/<id>/`. A ledger bundle keeps the ledger's own status and archive workflow.
- `unassign` ends the assignment as `unassigned` and clears focus when it was on that task.
- `promote_task` moves a live ephemeral bundle into its project's `.ledger/` with an index row. The task keeps its id, assignments, focus, and thread.
- Each task records once when it became the organization's obligation and when and how it closed. `take_task`, `assign`, and `hire` with a goal open a task when they create it; `ledger_add` sends `task_opened`. An ephemeral task closes `done` when its last assignee finishes; a ledger task closes when `ledger_status` archives it as `done` or `cancelled`, which sends `task_moved`. A task created before these records existed opens when first recorded. Fitness history reads these records rather than the current files. The ledger tools send nothing when `PI_SESSION_STATE_DISABLED=1` or no state database exists.

An assignment to a person at home saves first, then calls the person in: beside the assigning session's pane, or, for the operator, beside the attached tmux pane that Agent World supplies. If the wake fails, the result says that the assignment was saved.

## Manager tools

A session whose role manages, or an unroled organization root, gets eleven more tools: `meet`, `end_meeting`, `assign`, and `unassign` (above), and seven lifecycle tools. `hire` (required `role` and `goal`, optional `cwd` defaulting to the manager's directory, optional `name` and `session_id`) hires a person that reports to it, takes the given role at its first start, and receives a unique two-part human name from the session-title extension. It opens in a tmux window after the manager's pane, or headless outside tmux. `call_in(person, goal?)` reopens a person at home with its stored role and work, optionally assigning a new goal, and `rehire(person, goal?)` does the same for a former member, bringing it back into the organization (each refuses the other's case); `send_home` closes a running one; `rename` (`person`, `name`) renames a running one through its bridge without changing its id or history; `move` (`person`, `manager`) moves a person, with everyone under it, under another manager of the same organization (refused for a cycle, a stranger, or the person itself), tells its running bridge so later close notices go to the new manager, and mails the person and both managers; and `let_go` (`person`, `reason`) waits until the person is idle (calling it in when it is at home), asks it for a handover in one turn, and posts that reply verbatim in its team channel. Then it records when and why the person left, closes it, and moves it to the directory's former members, from which a manager's `rehire` brings it back. A failed or cancelled handover leaves the person in the team. `person` and `manager` accept a name in the caller's organization or a session id. Start and reopen send the manager's pane and id. A hire without a goal or into a role the catalog lacks fails before any window opens. A task is assigned before the person's first turn; the written goal is delivered through its task context, not passed as a command-line prompt. When its manager's team channel has messages, a new hire also gets one mail with that history before its first turn. Every root session registers the eleven tools, but only a managing role or an unroled recorded organization root keeps them active. Root-session lifecycle hooks restore the directory, mail, and task tools for every root and the eleven manager tools for managers, including when Pi resumes an older transcript whose saved tool set lacks them.

## Reading a transcript entry

Any client can ask the runtime for one entry of a session's transcript by sending `{"type": "read_entry", "requestId": ..., "sessionId": ..., "entryId": ...}` on the socket. The runtime reads the entry from the session's JSONL file and answers on the same connection with `{"type": "entry", "requestId": ..., "entry": {...}}`, or with `"error"`: `unknown session`, `session has no transcript file`, `entry not found`, or why the file could not be read.

## Reading history a page at a time

To scroll a conversation from the newest message up, send `{"type": "read_entries", "requestId": ..., "sessionId": ..., "limit"?: n, "before"?: entryId}`. The page is keyed by the session's `messages` index: its message entries (`part` `""`) ordered by `at`, then by when they were indexed. Without `before` the runtime returns the newest `limit` entries (50 by default); with it, the `limit` entries just before that entry. It reads the JSONL once per page, whatever the page holds, and answers with `{"type": "entries", "requestId": ..., "entries": [...], "before": ...}`: the entries in transcript order, oldest first, and in `before` the cursor for the page before (the first entry's id), or `null` when the page starts at the first indexed entry. Indexed ids the transcript no longer holds are left out and listed in `"missing"`. Errors are the same as for `read_entry`, plus `unknown cursor` when `before` is not an indexed entry of that session. Only indexed entries are paged, so a turn still running is not there yet.

## Live replies

A reply can be shown while the agent writes it. A client subscribes on its own socket connection with `{"type": "subscribe", "sessionIds": [...]}`; the runtime confirms with `{"type": "subscribed", "sessionIds": [...]}` and from then on relays the reply streams of those sessions on that connection. A new `subscribe` replaces the connection's earlier one, and an empty list ends it. Connections that never subscribe (bridges, command senders, readers) receive no stream.

The bridge forwards each piece of assistant reply text from Pi's `message_update` (`text_delta`; thinking and tool-call arguments are not forwarded), and the runtime relays it as:

- `{"type": "reply_delta", "sessionId": ..., "streamId": ..., "seq": n, "delta": text}`: append `delta` to the reply shown for `streamId`. One stream is one assistant message; `seq` counts its deltas from 1.
- `{"type": "reply_end", "sessionId": ..., "streamId": ..., "messageEntryId"?: id}`: the stream is over. Replace the streamed text with the transcript entry `messageEntryId` names (Pi's `turn_end` names it; it is already indexed and readable with `read_entry`). It is absent when Pi recorded no entry, as for a reply that failed or was aborted before it was saved; the session's history then holds what was kept. An end also closes every earlier stream of that session that never got one.

Streamed text is transient: it is never written to `events` or `messages`, is not sent again after a reconnect, and is lost while the runtime is down; the transcript entry is the record. Only the session's current generation is relayed.

No reader can hold up a writer. When the bridge's own socket to the runtime is full, it joins the stream's deltas into one held delta until the socket drains, so Pi's stream never waits. The runtime does the same for each subscriber: when a client's socket is full (Node's default write buffer), the runtime writes it nothing more until it drains, and holds per session only the newest stream's text, joined into one delta, and the last end. A coalesced delta carries the text of several, and its `seq` is the last one's, so `seq` may skip, but a stream's text arrives in order and whole as long as the client drains before that session's next reply starts. A client still behind then loses the older stream's held text and that stream's own end (the newer end closes it), and reads that reply from history. Either way, what the runtime holds for a client is at most one reply's text and one end per subscribed session; it picks no size limit of its own.

## Runtime outage

A session never depends on the runtime. While the runtime is down, a bridge keeps its session's current state and retries the socket, starting a new runtime if none answers. On reconnect it sends that whole state again: identity, run state, facts, the tool running now, and every conversation row (rows already indexed are ignored). Events that happened while nothing listened are not reconstructed. Instead the runtime records one `gap` event for the incarnation, from the last thing its bridge reported to the reconnect. A bridge that started a runtime will start another if that one dies too. A `/reload` is a short gap of the same kind.

## Liveness

An incarnation is `alive` while its bridge is connected and heard within the last five seconds. When the bridge goes quiet or its connection drops, the runtime checks the process itself (pid plus start time, so a reused pid does not count): a running process is `alive_bridge_lost`; a gone process ends the incarnation as `lost`. A check that fails (for example, `ps` cannot run) proves nothing: the incarnation stays `alive_bridge_lost` and a `process_check_failed` event is recorded. A clean shutdown ends it as `exited`. A `/reload` keeps the same incarnation. Reopening a session from a new process starts the next generation; the previous one ends as `superseded` and stays under watch until its process is gone. Only the current generation's bridge changes the session's run state.

## Running from source

The runtime runs this package's TypeScript directly: `node --import register.mjs runtime-main.ts`, using Node's built-in type stripping (on by default from Node 22.18) and a resolve hook that maps `./x.js` imports to `./x.ts`. Node does not strip types inside `node_modules`, so this works for a local checkout and a Pi git package, the two install paths the README documents.
